# 後端效能驗證

2026-09-12：以本次修改前的工作區版本為基準，在同一台機器比較。

## 改動

- OLE 清單以單次投影片掃描建立關聯索引，避免每個嵌入物件重新掃描所有投影片；預覽關聯仍沿用原本的判定邏輯。
- 列出物件時只讀取 CFB 簽章，檔案大小取自 ZIP 目錄。封裝的完整 CRC 驗證仍會先執行。
- 修復與 OLE 回寫以 1 MiB 區塊複製未修改的 ZIP 項目，保留內容、壓縮方式與項目中繼資料，避免一次配置整個大型媒體的記憶體。輸出仍以暫存檔完成後原子發布。

## 合成測試結果

| 工作負載／指標 | 修改前 | 修改後 |
| --- | ---: | ---: |
| 列出 80 個 OLE（每個 128 KiB，各位於一張投影片），耗時中位數 | 0.2736 秒 | 0.0131 秒 |
| 同一 OLE 清單工作負載，Python 配置峰值 | 0.61 MiB | 0.40 MiB |
| 修復含 32 MiB 未修改媒體的簡報，Python 配置峰值 | 32.27 MiB | 2.27 MiB |
| 同一修復工作負載，耗時中位數 | 0.0229 秒 | 0.0286 秒 |

此樣本的 OLE 清單約快 21 倍；大型媒體修復的配置峰值約減少 93%。分塊複製主要改善記憶體用量，此次樣本的修復耗時略增。

執行目前版本的基準：

```sh
python3 scripts/benchmark_backend.py
```

腳本在暫存目錄產生 ZIP_STORED 合成簡報，計時取三次執行的中位數，另以 `tracemalloc` 量測一次 Python 配置峰值。計時包含 CRC 驗證；不包含真實 Origin 編輯、VM 啟動或 EMF 渲染。配置峰值不是整個程序的 RSS；實際速度取決於檔案結構、壓縮方式與儲存裝置。

## 正確性檢查

新增測試涵蓋 OLE 清單與關聯結果、重複掃描消除，以及分塊複製的內容／中繼資料保留。修復與回寫都驗證了未修改媒體不被整筆讀取，並模擬寫入中途失敗，確認不發布不完整輸出、不殘留暫存簡報且不改動原稿。
